# 0010. VAT and the IOSS change

Status: accepted, 2026-11-04 (step 6.2, decisions C10, C18 and C22)

## Context

The facts are in `docs/facts/vat.md`, read on the authorities' pages on 2026-11-03. Its rule:
no rate from memory. Every rate below is copied from its table, with its source key.

What the shop must do, from that note:

- **A buyer in Norway**, on the web or at the counter, pays Norwegian VAT: 15 % on beans
  (food), 25 % on equipment (standard), included in the shown price (NO-rates, NO-hb5).
- **A buyer in Sweden, Denmark or Finland** gets an export from Norway at 0 % Norwegian VAT
  (NO-hb6). The buyer's country collects its own VAT at import, unless the seller uses IOSS.
- **IOSS** is optional. Under it, the seller charges the destination country's rate at
  checkout. It covers only consignments of at most EUR 150 (goods without freight, counted per
  parcel), and not goods subject to excise duties (EU-guide, DK-school).
- **Rates change by date**: Sweden's food rate on 2026-04-01, Finland's standard rate on
  2024-09-01 and its food rate on 2026-01-01. "Rates are rows with dates, never constants."

What the data fixes:

- **One gross price.** A payment is `qty * unit_price`: PAY-1 is 1157.00 for O-101
  (2 × 129.00 + 899.00). The frozen prices and payments cannot change (D4). The owner chose
  one gross price for every buyer (2026-11-04), so VAT is a share of the price, never added
  on top.
- **A web order with no country.** C-05 (Lars) has no country, and O-105 is his web order,
  paid by PAY-5. The app cannot refuse it.
- **No VAT column in contract A.** `tiny`'s columns are frozen (D13).

The DevOps route (map §3) builds its whole story on this module. Phase 8's pull request
changes how a foreign buyer is charged, behind a flag keyed on the customer's country. The
night it fails, a customer with no country reaches the new lookup and checkout returns a 500;
the postmortem adds a test with a customer with no country. So phase 8 must find, in 6.3's
code, one place to change and one case it can break.

## Decision

**The rates are dated rows** in the app db, table `vat_rates`, seeded from `vat.md`. They
are never a setting (ADR 0014).

| column | type | note |
|---|---|---|
| `country` | text | NO, SE, DK, FI |
| `kind` | text | the tax's kind: `standard` or `food` |
| `valid_from` | date | first day, included |
| `valid_to` | date or null | first day no longer valid; null means still valid |
| `rate` | decimal | per cent, as `vat.md` writes it |

Half-open periods, as `prices` has them. The seed:

| country | kind | rate | valid_from | valid_to | source |
|---|---|---|---|---|---|
| NO | standard | 25 % | 2024-01-01 * | | NO-rates |
| NO | food | 15 % | 2012-01-01 | | NO-hb5 |
| SE | standard | 25 % | 2024-01-01 * | | SE-rates |
| SE | food | 12 % | 2024-01-01 * | 2026-04-01 | SE-rates |
| SE | food | 6 % | 2026-04-01 | 2028-01-01 | SE-news |
| DK | standard | 25 % | 2024-01-01 * | | DK-rate |
| DK | food | 25 % | 2024-01-01 * | | DK-rate |
| FI | standard | 24 % | 2024-01-01 * | 2024-09-01 | FI-changes |
| FI | standard | 25.5 % | 2024-09-01 | | FI-changes |
| FI | food | 14 % | 2024-01-01 * | 2026-01-01 | FI-rates |
| FI | food | 13.5 % | 2026-01-01 | | FI-changes |

\* `vat.md` does not confirm when this rate started (its open point 3). The rate is the
note's; only the date is a choice of representation: 2024-01-01 is the first day of
`prices`, the earliest day the shop trades. The seed file marks each such row.

**A product's kind maps to the tax's kind** in one frozen mapping in `vat.py`: `beans` to
`food`, `equipment` to `standard` (`vat.md`, "Is roasted coffee food?" and the equipment
line).

**The functions**, all in `roastery/vat.py`:

```python
Scheme = Literal['domestic', 'export']


def scheme_for(order: Order, on: dt.date) -> Scheme:
    """How this order is taxed on this day (C22)."""
    return 'domestic' if order.head.country == 'NO' else 'export'


class VatRates:
    """The dated rows, read from the store once per command."""

    def rate_on(
        self, country: Country, kind: Kind, on: dt.date
    ) -> Decimal: ...

    def vat_of(
        self,
        gross: Money,
        country: Country,
        kind: Kind,
        on: dt.date,
        scheme: Scheme,
    ) -> Money:
        """The VAT share of a gross price, to the øre."""
```

- `scheme_for` takes the order being placed and the day (C22, which amends C10's signature),
  and returns `export` for every foreign order in the simulated years. Its body is the one
  line phase 8 changes; the callers stay as they are.
- `vat_of` under `export` is zero in the gross price's currency, with no lookup.
- `vat_of` under `domestic` takes the rate on the day and gives
  `gross * rate / (100 + rate)`, rounded to the øre, half up (`Money.to_ore`, ADR 0004).
  A negative gross (a credit order's line, S14) gives a negative share.
- `rate_on` raises when no row covers the day. It has no default country and no default
  kind: `country` is a `Country`, never `None`.

**The caller decides the country.** `Checkout.place` (`roastery/checkout.py`) works it out
once per order, in plain sight. The order's date uses the same answer (ADR 0008):

```python
def order_country(
    channel: Channel,
    found: Ok[Country] | Err[NoCountry | UnknownCustomer],
) -> Country:
    if channel == 'shop':
        return 'NO'           # the counter is in Bergen
    match found:
        case Ok(country):
            return country
        case Err(NoCountry()):
            return 'NO'       # C-05's O-105: Norway, on purpose
        case Err(UnknownCustomer() as why):
            raise NoSuchCustomer(why.customer_id)
```

- Channel `shop` means Norway, whoever buys.
- A customer with no country gets Norway's rate here, explicitly. The lookup never falls back.
- Then, per line: `rates.vat_of(line_gross, country, kind, day, scheme_for(order, day))`, where
  `day` is the order's local date (ADR 0008).

**What the app db stores from 6.3** (C18): `orders.vat_amount`, the sum of the lines' VAT
shares, in NOK. It is in the app db only and never exported. Contract A gets no VAT column;
S12 keeps the new tables editable until 1.0 if the owner later wants VAT in `month` or
`full`.

**Phase 8's migration** (not built now) is an expand and contract:

1. Expand: add `order_lines.vat_rate`; write both it and `orders.vat_amount`.
2. Backfill each old line with the rate it was charged under its scheme: Norway's rate for its
   kind on its day for a domestic line, 0 for an export line.
3. Switch the receipt and the accounting export to read the line's rate.
4. Contract: drop `orders.vat_amount`. One amount per order cannot say which rate each line
   had.

## Alternatives refused

| alternative | why refused |
|---|---|
| rates as settings or constants (`VAT_NO = 25`) | rates change by date (SE 2026-04-01, FI 2026-01-01); the DevOps route teaches "VAT rates are data, not a secret and not a setting" |
| a net price with each country's VAT added on top | the buyer's price would vary by country; PAY-1 would no longer be `qty * unit_price`, and the frozen payments break (D4). The owner chose one gross price |
| a separate price list per country | the same break, and `prices` is frozen |
| refusing a web order without a country | O-105 is in the frozen week, paid by PAY-5 |
| a fallback inside the lookup (`rate_on(None, ...)` gives Norway's) | hides C-05's case where nobody reads it. It is the shape of the bug phase 8's night is about; the lookup must stay strict so that the case has to be said |
| the scheme decided in each caller (`if country == 'NO'`) | the IOSS change would edit every caller: the `one-reason-to-change` twin's four places |
| `order_lines.vat_rate` from 6.3 | phase 8's migration would have nothing to expand; the DevOps `deploy-strategies` page needs the move from an order amount to a line rate |
| rounding the order's sum once instead of each line | the receipt shows VAT per line, and phase 8 moves the rate to the line; a per-line share is what the migration can backfill exactly |

## Consequences

- No order of the simulated years reads a foreign row: every foreign sale is `export`. The SE,
  DK and FI rows are seeded for the history and for phase 8, and an unused row is not a bug.
- VAT by country and kind changes `vat.py` and the seed rows only.
- Every foreign order's `vat_amount` is 0.00; a credit order's is negative.
- **For phase 8, not built now** (from `vat.md`):
  - IOSS covers a consignment of at most EUR 150, without freight, per parcel. Above it, the
    sale stays `export`. The value in EUR needs `fx_rates`, an outside feed (ADR 0012).
  - A business buyer abroad is always invoiced at 0 % and settles import VAT on its own
    return. IOSS is for consumers.
  - Danish coffee excise may keep coffee out of IOSS altogether (`vat.md` open point 1). Until
    it is settled, the app must not promise a landed price for Danish buyers.
  - Under IOSS, the EUR 3 duty per item and the EUR 2 handling fee land on the roastery or its
    carrier. They are costs, not VAT, and not in `vat_of`.
  - The rows' starred dates (open point 3) are never applied before the flag is on. The flag is
    turned on after the simulated years end (December 2026), so only rows in force from then
    on matter.
- **How the night story and the explicit case both hold.** The resolution to Norway lives in
  `order_country`, in checkout. Phase 8's pull request reads `customer.country` for the flag
  check (the flag is keyed on the customer's country) before `order_country` runs; with C-05 that
  value is `None`, and the flag client's lookup fails. The flag did not help because the
  lookup ran before the flag was asked. The case must stay in 6.3's code for that to be true.
  A `None` passed straight to `vat_of` would be caught by the type checker, so phase 8 writes
  the bug where the types do not reach (the flag client's context).
- `scheme_for(order, on)` takes the order, not a country (C22). Under IOSS the scheme depends
  on more than the country: on the consignment's value in EUR, on the buyer's `account_kind`,
  and perhaps for Denmark on the product's kind. The order carries all of these, so phase 8
  widens the body of `scheme_for`, and the one caller in `Checkout.place` stays as it is. The
  flag client is a new argument or a wired port; either way it is still one module.
- **Open question:** Denmark's rows rest on Den juridiske vejledning 2026-2; its 2024 and
  2025 editions were not read (`vat.md`). Harmless while every Danish sale is `export`; to be
  read before phase 8 relies on them.
- **Note for phase 8:** map §3 says to "backfill old lines with Norway's rate by kind". That
  predates the export framing: an export line carried 0 %, as step 2 above says.
- 6.2 §5's open item stands: phase 8's test story ("Finland falls back to Norway's rate") is
  re-fitted there.
