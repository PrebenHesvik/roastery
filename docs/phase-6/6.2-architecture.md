## 1. Context

6.3 writes code against this step. 6.4 freezes what the simulator calls. Phase 7 points the pages at module names and line numbers. So 6.2 fixes three things on paper:
- the home of each of the 35 pages;
- the choices every module stands on;
- the call surface (contract B) as typed signatures.

The owner reads `architecture.md` before 6.3 starts.

The vocabulary for the seams comes from the `codebase-design` skill. A port is a real seam only when two adapters stand at it: memory and sqlite; the API and the simulator; sequential ids and scripted ids. A module that fails the deletion test is named as a pass-through and is not built.

## 2. Decisions for this step

The prefix is C, for contract C; A and B are the other two contracts.

| # | decision | why |
|---|---|---|
| C1 | **A flat package** `roastery/*.py`. A layer is a row of `LAYERS` in `architecture.py`, not a folder; `PACKAGE = 'roastery'`; no `without/` in the app | the pages key on `roastery/pricing.py`; `import_graph` globs `*.py`; longer import paths cost 72-character lines (G16); a folder would only repeat `LAYERS` (the deletion test) |
| C2 | **No third-party dependency in `packages/shop`**. `reports.py` returns rows, never frames; polars stays in data-docs' `frames.py` | the pin pulls in no libraries; the layers page's violation stays teachable |
| C3 | **Persistence**: stdlib `sqlite3` behind hand-written repositories and a unit of work, with a memory twin of every store. The outbox row and the `customer_changes` row are written in the same transaction as the change. The app db has its own schema; the extracts are projections of it | plan §5; the patterns show without an ORM; the second adapter makes the repository seam real |
| C4 | **Domain types**: frozen dataclasses; ids as value types; `Money(amount, currency)` on `Decimal`. `Qty` is a whole number other than zero, negative only through `Checkout.credit_for` | the value-objects page; S14 needs a negative line, and a second type for that one case would be a shallow module |
| C5 | **The order**: one class per feed status (`Placed`, `Paid`, `Invoiced`, `Shipped`, `Delivered`, `Cancelled`), with `TRANSITIONS` keyed on exactly those six. `Shipped` and `Delivered` carry how the order is settled (`Paid` or `Invoiced`). Paying an open invoice adds a payment row and no status event. A counter sale (channel `shop`, e.g. O-104) ends at `Paid`. A credit order (order 300, S14) is an order of its own, linked to the sale it returns | S13, S14; the state-machine page reads `order_events`, so the table and the feed must agree |
| C6 | **Errors**: a refused command raises one of a closed family `ShopError`, listed per service in contract B. A question with two kinds of answer returns a `Result`: `country_of` gives `NoCountry` or `UnknownCustomer`; parsing gives `ParsedLine` or `Reject`. The API maps `ShopError` to statuses | plan §5 asked for this to be weighed; a scripted driver wants a refusal to be loud and catchable by type (O-106) |
| C7 | **Ids and provenance**: every id comes through an `Ids` port (`next(kind)`). The API's adapter is a sequence; the simulator's is scripted (the script's ids in order, then sequential). The store refuses a duplicate id (`DuplicateId`). `source` is a wiring argument: the simulator wires the app twice over one store, once as `scripted` and once as `simulator`; the API wires `visitor`. **Replaces plan §2's "caller-supplied ids"** | the app makes E-01..E-11 and the movement and shipment ids itself, so ids passed in by the caller cannot cover the week; two adapters make the seam real; the domain never sees "scripted" |
| C8 | **The Clock** has only `now()`, in UTC. `order_date` is `local_date(now, zone)`, a pure function; the zone comes from the customer's country, and from `ROASTERY_SHOP_ZONE` at the counter | stamps are UTC; E-11 at 21:30 UTC is 7 October in Helsinki; a `today()` would hide the zone |
| C9 | **Events**: an in-process `EventBus` in core, with handlers subscribed in `bootstrap`. Every status change is a `StatusChanged` outbox row. `relay` is a job that sends batches of `ROASTERY_RELAY_BATCH` rows to the `StatusFeed` port. A batch that fails waits for the next run while later batches go; the feed adapter stamps `loaded_at`; order across batches is not promised | G15: the only mechanism that lands E-10 before E-09, with E-09 once; E-08's two days are a relay that did not run |
| C10 | **VAT**: rates are dated rows by country and kind in the app db (`vat_rates`, the four countries of `vat.md`), never a setting. **One gross price for every buyer** (owner, 2026-11-04). `vat_of(gross, country, kind, on, scheme)` gives the VAT share of a gross price. `scheme_for(country)` is a one-line policy that returns `export` for every foreign country in the simulated years. Channel `shop` means Norway. **A customer with no country (C-05's O-105) gets Norway's rate, explicitly, never as a fallback inside the lookup**; the phase 8 change must keep that case (its postmortem story) | phase 8's PR changes `scheme_for` and the rate rows, not the callers; a gross price keeps D4 |
| C11 | **Web tracking is an outside system** that the simulator writes; there is no `log_event` in the app. **Replaces plan §2's "`log_event` with source, variant and step"** | `contract.md` already files `web_events` and `web_visits` under web tracking; the deletion test: a service that only appends rows nothing reads adds nothing |
| C12 | **Contract B** is the services on `App`, one class per service module. A command is a frozen dataclass only where it carries lines (`PlaceOrder`, `PaymentMessage`); other calls take keyword arguments. Jobs have their own section and take no clock (the port is wired in). The signatures live in one fenced block of `architecture.md`. 6.3 writes a snapshot test (`inspect.signature` of each listed function, and the error family, against a committed list); 6.4 pins it | a freeze needs a mechanism; the owner reads it in one place |

- provider messages, which it delivers to `handle_message`;
